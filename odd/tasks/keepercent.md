## Day 2 — Mon Sep 21 (components)

- [x] T2.1 `GoalView`: drawing + hit-testing. The task originally read "frame areas enlarged beyond the stroke"; that was tried and **reversed after testing it by hand** — see the "what you see is what you tap" note below. Split into two work units, because the goal maths belongs in `Domain/` for the same reason as T1.2: the app target has no test target. `3ddc274` `GoalGeometry` (362 lines) + tests (279 lines) — delegated writer, strict TDD, RED shown before GREEN. `GoalPoint` deliberately does **not** clamp to `0...1`, unlike `CourtPoint`: on the court an out-of-range tap always means "somewhere on the court" and clamping loses nothing, but on the goal out-of-range *is* the information — it is what a post hit and a miss look like, and clamping would turn both into zones inside the frame. Tested tie-breaks, each deliberate: the corner belongs to the **post** (the crossbar spans *between* the posts, so its band's `x` is restricted to the mouth), a tap both high and wide reads as wide (`MissDirection` has no combined case), a tap below the ground line resolves onto it (the ball cannot pass under the floor), NaN resolves to the mouth centre. The writer flagged an open question that turned out to be a real defect: the post band had no upper bound on `y` while `region(for:)` stops at `-bandY`, so everything above the drawn region still hit-tested as the post — drawing and hit-testing had drifted, the exact thing `region(for:)` exists to prevent. **The round-trip test missed it because it only checked region centres**; it now asserts all four edge-inset points too. `d43d70d` `Keepercent/DesignSystem/GoalView.swift` — delegated writer; the parent then fixed two defects that a green build and 142 green tests could not see, both found by running it: the aspect ratio was computed in normalized units, **which are not square** (one `x` unit spans 3 m, one `y` unit 2 m), drawing a nearly square goal clipped at the bottom — fixed by converting both back to metres and using two independent axis scales from a single shared `layout(in:)` that drawing and hit-testing both read; and the 3×3 grid was drawn in the same colour and weight as the net, so the nine zones — the actual affordance — were invisible. `5ed48af` **user-found defect**: tapping the painted black post recorded `inside.middle.left`, because the stroke was centred on the mouth's edge and half its width fell inside. The frame is now *filled* as exactly the region `GoalGeometry` resolves to `.post(...)` — **what you see is what you tap**: one out band, one frame, one mouth, where before there were four bands and no way to tell where the post ended. The drawn post is deliberately not to scale (a real post is ~8 cm against a 3 m mouth). `28c78ab` the review's two advisory findings, both verified and applied: `GoalGeometry.init` now traps a degenerate geometry, because a zero width made the band thickness infinite and every tap would have silently resolved as a post hit — a quiet wrong answer that corrupts recorded data, where a trap is loud and correct; and the dead upper bound in `insideMouthY` (already guaranteed by `groundResolvedY`) was removed rather than left looking protective, plus four tests resolving targets against a non-default 4×2 geometry, since every earlier test used only `.standard`.
